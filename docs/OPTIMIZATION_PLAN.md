# 项目优化路线

本文档用于记录当前项目的工程化优化方向，供队友分工、排期和验收使用。

## 1. 总体判断

本项目是一个功能面较完整的比赛型全栈项目，包含 Django/DRF 后端、Vue/Vite/Electron 前端、Celery 异步任务、Redis、MySQL、FFmpeg 和 AI 服务。

当前最需要解决的不是继续堆功能，而是让项目具备以下能力：

1. 新成员可以按文档稳定搭建环境。
2. 核心视频流程可以完整跑通并重复演示。
3. 异步任务失败后可以定位、重试和恢复。
4. 权限、上传和第三方密钥不会成为明显风险。
5. 关键业务有测试和构建检查作为质量门槛。

暂不建议现在更换技术栈、拆分微服务或大范围重写前端。对于当前项目规模，这些工作投入较大，但不能优先解决启动和验收问题。

当前结论：项目核心功能目前具备继续开发和演示的条件。下列内容同时包含已修复问题、当前环境阻塞、工程风险和待验收项，不应全部理解为“项目不可用”。

## 2. 当前状态、已验证问题与待确认项

以下结论来自当前代码检查、构建检查和运行验证，应作为后续工作的起点：

- **已修复阻断**：前端搜索页曾重复声明 `const response`，会导致 `npm run build` 失败；现已修复并验证构建通过。
- **当前环境阻塞**：业务数据库的 Django 检查、数据库检查和迁移计划检查已通过；全量测试创建 `test_video_dev` 测试库时仍遇到 MySQL 1044 权限错误，需要管理员授权测试库，不能据此断言业务主流程不可用。
- **安装风险**：原始 Python 依赖包含 GPU 版 Paddle 和 NVIDIA 依赖，Windows/CPU 新成员不适合直接安装，需要独立的 CPU 安装方案。
- **质量缺口**：`authentication`、`ai_service`、`core`、`users` 的测试覆盖仍较少，说明质量门槛不足，不等于这些模块已经失效。
- **待验收项**：视频、AI 和弹幕等模块需要按真实主流程继续验收；在没有可复现失败证据前，不将它们描述为整体不可用。
- **工程风险**：视频处理涉及多个 FFmpeg/ffprobe 调用，仍需统一检查参数校验、路径处理、超时和失败恢复。
- **维护性风险**：前端存在较多大页面、重复请求逻辑和本地状态处理，主要影响后续维护效率，不是当前构建阻断。

## 3. 优先级规划

### P0：先恢复可运行基线

这一阶段完成前，不建议开展大规模重构。

#### 3.1 修复前端构建

状态：已完成。搜索接口已确认使用 `/videos/videos/`，重复声明已移除，`npm run build` 已通过；当前仅保留大 chunk 的性能提示。

- 修复搜索页面重复的 `response` 变量声明。
- 确认搜索接口和视频列表接口的调用意图，避免只改变量名而保留错误接口。
- 执行 `npm run build`，将构建通过作为前端合并门槛。

验收标准：前端依赖安装成功，生产构建成功，没有 TypeScript/Vite 编译错误。

#### 3.2 完成数据库和缓存环境验证

状态：部分完成。当前虚拟环境下 Django 配置检查、数据库检查和迁移计划检查通过；全量测试创建测试库仍需要数据库管理员授权，Redis 和完整主流程还需在团队目标环境中复核。

- 由数据库管理员为开发账号补充 `test_video_dev` 测试库的创建/访问权限，并复核目标库的迁移权限。
- 执行 Django 配置检查、迁移计划检查和数据库迁移。
- 验证 MySQL `SELECT 1`、Redis `PING`。
- 不把数据库和 Redis 密码写入代码、文档或 Git。

验收标准：新成员按照 `docs/DEVELOPMENT.md` 配置后，可以完成迁移并启动后端。

#### 3.3 固化 Python 依赖方案

状态：待完成。当前虚拟环境已能运行基础检查，但 CPU 依赖文件还没有固化。

- 保留原始依赖文件作为项目依赖来源记录。
- 增加 Windows/CPU 开发环境的安装说明或独立依赖文件。
- 明确 Python 3.12 是当前团队开发版本。
- 将 AI 相关的重型依赖和可选依赖标注清楚，避免队友无法区分“启动必需”和“功能可选”。

验收标准：队友不需要 NVIDIA 环境，也能安装依赖并启动基础后端。

#### 3.4 启动自检与健康探针

状态：已完成基础版本。项目提供以下运维检查：

- `/api/health/live/`：只检查 Django 进程是否能响应；
- `/api/health/ready/`：检查 MySQL 和 Redis，不满足条件时返回 HTTP 503；
- `start_dev.py`：启动 Django 后等待就绪探针，启动前端后等待 5173 端口，未完全就绪时报告降级状态；
- AI 服务入口按需加载，避免模型依赖阻塞基础启动检查。

后续仍需在团队目标环境中执行一次完整启动和主流程验收。

### P1：稳定视频业务主链路

#### 3.5 明确视频状态机

建议统一视频生命周期，示例：

```text
上传中
  -> 转码中
  -> 待审核
  -> 审核通过
  -> 已发布
  -> 播放/互动
```

同时明确失败、拒绝、删除等状态。所有接口、后台任务和前端展示都应使用同一套状态定义，避免各处散落字符串判断。

验收标准：可以根据数据库状态准确判断视频当前阶段；异常状态不会被误显示为已发布。

#### 3.6 整理异步任务流水线

建议把视频处理拆成可追踪的步骤：

```text
上传 -> 转码 -> 生成封面 -> 字幕处理 -> AI 分析/审核 -> 发布
```

每一步都应具备：

- 明确的开始、成功、失败状态；
- 失败原因和日志；
- 合理的超时和重试次数；
- 幂等处理，重复执行不会生成重复数据；
- 管理员可查看任务状态，必要时手动重试。

验收标准：单个步骤失败时，可以定位失败原因并重新处理，不需要手工修改数据库。

#### 3.7 统一媒体文件管理

- 限制上传文件大小、格式和文件名。
- 统一生成媒体文件路径，避免用户输入直接参与路径拼接。
- 删除视频时同步处理相关媒体文件。
- 增加孤立文件清理方案。
- 将本地文件存储封装成独立接口，为以后接入对象存储留出空间。

验收标准：上传、转码、播放和删除流程不会产生明显的脏文件或路径异常。

#### 3.8 让 AI 功能可选且不阻塞主流程

AI 摘要、识别、审核等能力应当视为可选处理步骤：

- AI 服务不可用时，视频上传、转码、审核和播放主流程仍然可用；
- 模型加载和调用尽量放到异步任务或独立服务中；
- 记录模型调用耗时、失败原因和重试信息；
- 通过环境变量或功能开关控制是否启用具体 AI 能力。

验收标准：缺少某个 AI 服务时，基础视频业务可以启动并正常演示。

### P1：权限和安全收口

#### 3.9 后端权限必须是最终判断者

- 前端路由守卫只负责界面体验，不能代替后端权限校验。
- 普通用户、VIP、管理员和超级管理员的能力范围应形成权限表。
- 超级管理员的系统设置、管理员管理和数据库相关功能应默认关闭或严格限制。
- 关键管理员操作记录审计日志。

#### 3.10 审计外部命令和上传入口

重点检查 FFmpeg/ffprobe 调用：

- 禁止通过 shell 字符串拼接用户输入；
- 对输入路径、文件名和参数做白名单校验；
- 设置进程超时和资源限制；
- 记录命令失败原因，但不要把敏感配置写入日志。

同时检查上传文件的真实类型、大小、保存路径和下载响应头。

#### 3.11 管理密钥和配置

- 所有数据库、Redis、邮件、支付和 AI 密钥使用环境变量。
- `.env`、虚拟环境、`node_modules`、日志和媒体文件不得提交。
- 测试密钥也不要继续留在共享 Git 历史中；如果曾经公开过，应考虑轮换。

### P2：前端维护性和体验

#### 3.12 统一 API 和状态处理

- 统一封装 HTTP 请求、错误处理和鉴权失效逻辑。
- 避免同一接口在多个页面重复实现。
- 统一 loading、空数据、错误和重试状态。
- 统一浏览器、Electron 和开发环境的 API 地址配置。
- 视频处理状态使用统一的轮询或 WebSocket 机制。

#### 3.13 拆分大页面

优先拆分视频详情、后台管理、搜索等复杂页面，把上传、审核、评论/弹幕、AI 结果等内容拆成业务组件或组合式函数。

拆分时保持接口行为不变，避免一边重构组件一边修改数据库和接口，降低排查难度。

## 4. 测试和质量门槛

建议先补最有价值的业务测试，而不是追求测试数量：

- 注册、登录和鉴权失效；
- 普通用户访问管理员接口时被拒绝；
- 视频上传和状态变化；
- 转码任务成功、失败和重试；
- 审核通过后才允许发布；
- 删除视频时数据库和媒体文件保持一致；
- AI 服务不可用时主流程仍能工作。

最终至少保留一条端到端冒烟流程：

```text
注册/登录 -> 上传视频 -> 转码 -> 后台审核 -> 发布 -> 播放
```

建议在 CI 中逐步加入：

1. Django 配置检查；
2. 后端核心测试；
3. 前端生产构建；
4. 依赖和敏感信息检查；
5. 数据库迁移检查。

共享数据库的集成测试应串行执行，并保留第一处失败信息，避免并发测试互相污染。

以下事项可以记录，但不应抢占当前主线：

- 更换 Django、Vue 或数据库技术栈；
- 拆分成多个微服务；

## 7. 推荐执行顺序

```text
固化软件工程核查结论
  -> 统一后端错误协议和错误码
  -> 统一前端请求层和错误展示
  -> 增加 request_id 并打通日志追踪
  -> 整理视频状态机和异步任务失败恢复
```

优化完成的判断标准不是“页面更多”，而是队友能复现环境、用户能完成主流程、任务失败能恢复、问题出现能定位。

## 9. 统一错误与可观测性目标

### 9.1 后端错误协议

第一轮只统一错误响应，不强制包装所有成功响应，减少对现有前端的破坏。目标格式：

```json
{
  "success": false,
  "error": {
    "code": "VIDEO_NOT_FOUND",
    "message": "视频不存在或无权访问",
    "fields": {},
    "request_id": "req_xxxxx"
  }
}
```

约束如下：

- `code` 是稳定的机器可读错误码，不能直接使用中文句子；
- `message` 是可以展示给用户的中文信息；
- `fields` 只用于表单字段校验，没有字段错误时为空对象；
- `request_id` 用于关联前端反馈、Django 日志和 Celery 日志；
- 详细异常堆栈只进入服务端日志，响应中禁止出现原始 `str(e)`、文件路径、密钥、SQL 或依赖内部信息；
- 先覆盖登录、权限、视频上传/查询、转码触发、审核和发布等主链路，再逐步迁移低频接口。

### 9.2 前端统一错误处理

前端保留一个公共 HTTP 客户端，并统一转换为 `AppError`：

```text
AppError = code + message + fields + requestId + httpStatus
```

公共请求层负责：

- API 基础地址和超时配置；
- Token 附加、刷新和登录失效处理；
- 网络断开、超时、401、403、404、429、500 等通用提示；
- 兼容迁移期间旧接口的 `detail/error/message/字段字典`；
- 记录 `request_id`，方便用户反馈时复制问题编号。

页面只处理当前业务特有的状态，不再重复解析 Axios 原始错误。所有直接 Axios、硬编码 `localhost` 和可替代的直接 `fetch` 调用应逐步迁移到公共请求层。

### 9.3 日志和异步任务约束

- 每个 HTTP 请求生成或接收一个 `request_id`，响应头、错误体和日志统一携带；
- HTTP 请求触发 Celery 任务时，把 `request_id` 和 Celery `task_id` 一并记录；
- 异步任务统一使用 `pending`、`processing`、`succeeded`、`failed`、`cancelled` 等有限状态；
- 每个任务明确超时、最大重试次数、可重试异常和不可重试异常；
- 用户只看到安全的失败原因，管理员可以通过问题编号查询完整日志；
- 操作日志写入失败不能影响业务请求，但必须使用正式 logger 记录，不能静默或只 `print`。

## 10. 已确定的产品开发方向

### 10.1 AI 从本地模型迁移到云端 API

后续默认不再把本地模型作为主要交付方式。Whisper、OCR、NSFW 等能力逐步迁移为云端 API，但不能直接把具体厂商 SDK 散落在视图和 Celery 任务中。

目标结构：

```text
业务流程 -> AI Provider 接口 -> 云端供应商实现
                         -> Mock/测试实现
                         -> 临时兼容的本地实现（迁移期）
```

迁移要求：

- 核心视频上传、转码、人工审核、发布和播放不能依赖 AI 服务可用；
- AI 服务通过配置和功能开关启用，缺少 API Key 时项目仍能基础启动；
- Provider 统一定义超时、重试、限流、成本记录和结果格式；
- 不在第一阶段立即删除本地实现，先完成接口抽象和回归验证，再逐项替换；
- 云端返回内容仍要经过服务端校验，不能直接信任或直接展示原始供应商错误。

### 10.2 UI 系统性优化

UI 优化是正式方向，但在错误协议和核心交互状态稳定后实施，不进行无边界的大规模重写。优化范围包括：

- 建立颜色、字号、间距、圆角、阴影和状态色等设计变量；
- 统一按钮、表单、表格、分页、弹窗、通知和导航的使用规则；
- 补齐 loading、空数据、错误、无权限、处理中、成功和可重试状态；
- 优先优化登录、首页/搜索、视频详情、上传创作、审核管理五条比赛演示路径；
- 统一浏览器和 Electron 的响应式布局、键盘操作、焦点状态和基础无障碍体验；
- 页面拆分与视觉优化分批进行，每批都必须保持接口行为和主流程可验证。

## 11. 分阶段实施计划

### 阶段 0：规划冻结

本阶段只确定问题、边界、顺序和验收标准，不修改业务功能。

验收标准：团队确认本文件是当前优化工作的统一入口；新增需求先判断是否影响基础主链路，不直接插入正在执行的工程治理阶段。

### 阶段 1：统一错误基础

工作内容：

1. 定义错误码目录和错误响应结构；
2. 增加 DRF 全局异常处理器；
3. 增加 `request_id` 中间件和响应头；
4. 建立前端 `AppError` 和唯一公共请求客户端；
5. 先迁移登录、权限、视频主链路接口；
6. 为错误结构、401/403、字段校验和未知 500 增加测试。

验收标准：同类错误在不同接口具有相同结构；前端不再为主链路分别猜测 `detail/error/message`；未知异常不会泄露内部内容，并可通过 `request_id` 定位。

### 阶段 2：任务状态与日志闭环

工作内容：

1. 明确视频状态机和 AI/转码任务状态；
2. 统一任务超时、重试和失败记录；
3. 打通 `request_id`、`task_id`、`video_id`；
4. 提供安全的失败提示和管理员重试入口；
5. 验证重复提交、Worker 中断、Redis 暂时不可用和处理超时。

验收标准：任一步骤失败都能知道失败位置、查询日志并安全重试，不需要手工修改数据库才能恢复。

### 阶段 3：测试、CI 与生产配置

工作内容：

1. 解决测试数据库权限或提供独立测试数据库方案；
2. 补认证、权限、上传、转码、审核、发布和删除测试；
3. 增加前端请求层和核心交互测试；
4. 建立 CI：后端检查与测试、迁移检查、前端测试与构建；
5. 增加 Lint、格式化和敏感信息检查；
6. 分离开发、测试和生产配置，收口 DEBUG、CORS、Cookie、HTTPS 和密钥设置；
7. 整理基础依赖与可选 AI 依赖。

验收标准：新提交不能绕过自动化质量门禁；生产配置不依赖开发默认值；新成员不安装本地 AI 模型也能运行基础业务。

### 阶段 4：云端 AI Provider 迁移

工作内容：

1. 定义字幕、OCR、内容审核和摘要 Provider 接口；
2. 增加 Mock Provider，保证无外部费用的自动化测试；
3. 接入选定的云端 API，并统一鉴权、超时、重试、限流和用量记录；
4. 按功能逐项灰度替换本地模型；
5. 验证云端服务不可用时主流程降级可用。

验收标准：切换供应商不修改业务视图；未配置云端密钥时基础系统可运行；调用失败不会卡死视频主流程。

### 阶段 5：UI 与比赛演示体验

工作内容：

1. 盘点并确定设计规范和公共组件；
2. 先优化比赛演示主路径，再处理后台低频页面；
3. 统一所有加载、空、错、权限和处理进度状态；
4. 拆分复杂页面，降低重复请求和重复样式；
5. 执行浏览器/Electron、常见分辨率和键盘操作验收；
6. 固化演示脚本和异常演示方案。

验收标准：评委可以顺畅理解主流程；关键操作有明确反馈；常见失败有可恢复入口；视觉和交互规则在不同页面保持一致。

### 阶段执行纪律

- 每次只进入一个主阶段，不同时开展大范围后端重构、AI 迁移和 UI 重写；
- 每个任务开始前确认 Git 状态，提交只包含当前任务；
- 每个阶段先补最小测试，再实施，再执行构建和回归；
- 未达到本阶段验收标准时，不用“功能看起来能用”代替完成结论；
- 每阶段结束后更新本文件中的状态、验证命令、结果和遗留风险。
